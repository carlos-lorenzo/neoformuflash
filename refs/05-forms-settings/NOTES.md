# 05 Forms & Settings

This folder defines the mechanical rules for data entry, modal constraints, and the typographical hierarchy required to organize dense settings pages without relying on heavy borders or cards.

*   **Grouped Settings (`linear_settings.jpg`):** Settings pages rely heavily on vertical whitespace and typography rather than bordered cards. Section headers use a larger font (approx. 18px, semi-bold) paired with 13px muted descriptive text. Distinct sections are separated by generous vertical margins (e.g., 40px–48px). Interactive elements (like toggles or dropdowns) are flush-right aligned against the container edge, keeping the left axis strictly dedicated to reading labels.
*   **Simple Input Modals (`linear_simple_popup_form.jpg`):** Standard data-entry modals are strictly width-constrained (approx. 400px–480px). Input fields use a 1px border with very low contrast against the background and an internal padding of about 8px 12px. Field labels are small (12px), use a secondary text color, and sit closely above the input field (approx. 4px gap) to strongly associate the label with the input. Primary and secondary actions are always right-aligned at the bottom.
*   **Long-Form Modals (`linear_longer_text_submission.jpg`):** When the primary task is drafting content (like an issue or document), the modal expands significantly (e.g., 700px–800px max-width) but the input field itself loses its borders. The modal canvas *becomes* the input. Structural elements like metadata tags, assignees, and the submit button are pinned to the bottom edge using a dense, horizontal flex layout (approx. 24px–28px pill heights) to keep the writing area unobstructed.
*   **Inline Editing (`linear_row_edit.jpg`):** When editing data within a list or table, the input field perfectly matches the height and typography of the static text it replaces (e.g., 32px height, 13px text). This prevents the surrounding rows from shifting or jumping when a user clicks in or out of the edit state.
*   **In-Context Form Validation (`vercel_invalid_input.jpg`):** Errors must be caught and displayed immediately at the point of interaction, preventing users from submitting invalid data (crucial for things like complex LaTeX inputs or structured metadata).
    *   **Visual Indicators:** Erroneous inputs receive a strict semantic treatment: a red border (`#E5484D` or similar) replaces the default focus state. 
    *   **Explicit Error Messaging:** Generic alerts are banned. Error text must appear immediately adjacent to or below the failing input inside a designated, red-tinted container. It must include an alert icon and explicitly state what went wrong (e.g., "Please enter a valid university domain").
    *   **Action Blocking:** The primary submission button (e.g., "Continue" or "Save") remains present but should visually reflect that the form cannot proceed until the inline error is resolved, keeping the user strictly focused on the correction.
